## 后续每次测试必须保存

每次建立独立子目录，名称采用执行时的真实时间与问题名，例如 `YYYYMMDD-HHMMSS-email-qa/`，时间按 Asia/Shanghai。不要覆盖旧记录。至少保存：

- `metadata.json`：开始和结束时间、完整测试命令、当前 commit、工作区是否有未提交变更及相关 diff；Python/依赖版本、平台、CPU、输入数据或 fixture 的 SHA-256。
- `output.log`：完整 stdout/stderr，包含失败、错误与退出码；必要时另存 JUnit XML。保留测试本身退出码，不能因重定向或 tee 错报成功。
- `metrics.json`：样本数、成功/失败数量、分项指标、耗时、明确单位、指标定义和失败样本 ID；指标不适用时写 null，不估算成实测。
- 真实模型运行额外记录实际 provider/model、生成参数、模型调用数、输入/输出 token、费用、缓存命中/未命中。使用运行时有效配置及账本核对，不只抄默认模型名。
- 需要分析流水线时，保留逐题预测、有效引用、搜索词、跳数、各阶段耗时；日志注明哪些字段未采集。不能为了日志未经讨论改变已确认的功能行为。

不保存 API key、认证信息、完整环境变量或 .env 内容。公开 GitHub 记录优先使用邮件 ID 和指标，避免复制无关个人邮件正文。模型缓存与账本目前是本地忽略文件，不能把“本地有缓存”等同于“已提交可追溯日志”；应提取不含密钥的相关记录到本目录。

## 怎么量化“提效”

新实验方案在对应题目的讨论中确认，实施后将基线与新方案都记录。对比保持同一数据、机器、模型、参数及缓存条件，明确仅变动哪个因素；重复计时并报告次数、均值/中位数和 p95，不把单次波动当作提升。

| 功能 | 待讨论的对照实验 | 指标 |
| --- | --- | --- |
| 日报并发 | 相同邮件与分类 prompt，串行对并发 | 端到端及分类耗时、吞吐、调用数、费用、摘要质量 |
| 倒排检索 | 同一 BM25 公式，全扫描对倒排查询 | 建索引成本、查询延迟、内存、相同得分与召回 |
| 多跳问答 | 一次检索对最多三次检索 | 一跳/两跳准确率、引用命中、延迟、调用数、费用 |
| 后续工具 | 根据功能确定对照，先定义任务成功 | 成功率、工具错误率、上下文占用、调用次数、审批负担 |

耗时降低率 = `(基线耗时 - 新耗时) / 基线耗时`；速度倍数 = `基线耗时 / 新耗时`。准确率差异使用“百分点”。模型费用和延迟区分冷缓存与热缓存；本地缓存重放不能用来宣传真实 API 加速。

## 可用于当前项目描述的措辞

“从零实现倒排索引与 BM25，在 2.6 万封邮件公开测试上实现平均 8.4 毫秒查询、17 个查询平均 recall@10 为 100%；构建最多三轮检索的邮件问答流水线，在 25 个公开问题上达到 92% 答案准确率。”

以上是历史本机单次测量，尚无提速对照。求职材料应注明公开样本及测量范围；后续完成可复现对比后，再补充实际提升幅度。
